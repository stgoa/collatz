# Rules for AI agents

These rules apply to every AI agent working in this repository: Claude, ChatGPT/Codex, Gemini, or any other. They also apply to humans. They replace the previous `AGENTS.md`, which is kept for the record in [`archive/AGENTS_2026-10-19.md`](archive/AGENTS_2026-10-19.md).

The repository is an open research notebook on the Collatz conjecture, mainly its *cycle* half. Anyone may contribute by pull request. Correctness of claims matters more than speed or volume.

## 1. Read first, in this order

1. [`README.md`](README.md): what the project is and how it is laid out.
2. [`docs/STATUS.md`](docs/STATUS.md): what is established, and at which status.
3. [`docs/FRONTIER.md`](docs/FRONTIER.md): the open targets, and where to push.
4. [`docs/CONVENTIONS.md`](docs/CONVENTIONS.md): notation, status labels, ID scheme and external inputs.
5. The `README.md` of the research line you will touch, e.g. [`experiments/cycle_spectrum/README.md`](experiments/cycle_spectrum/README.md).
6. [`CONTRIBUTING.md`](CONTRIBUTING.md): the pull-request workflow and step-by-step playbooks.

## 2. Where things go

| Content | Location | Format |
|---|---|---|
| A research line (programme) | `experiments/<line>/` | Must have a `README.md`: goal, status, an index of its results, how to verify |
| One result: a claim and its argument | `experiments/<line>/<id>/README.md` (legacy folders use `REPORT.md`) | Markdown with the status header of §4 |
| Code that checks or explores a result | Same folder: `check_<topic>.py` (verifier) or `probe_<topic>.py` (exploration) | Python 3, standard library only |
| Output of that code (a "receipt") | Same folder, named after its script: `check_<topic>.json`, `.csv` | Generated by the script; never hand-edited |
| Formal proofs | `lean/` | `.lean` sources; build and axiom receipts in `lean/receipts/`; the unit table in `lean/STATE.md` |
| Independent review or replication of someone else's claim | `reviews/<topic>/` | `README.md` with the verdict, plus scripts and receipts |
| Typeset write-ups | `papers/<slug>/<slug>.tex` | LaTeX source only; never commit build artifacts |
| Repository-wide documentation | `docs/` | Markdown |
| Shared tooling | `scripts/` | Python 3 |
| Finished history | `archive/` | Frozen: never edited |

The repository root holds only:
- the files `README.md`, `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md` and `LICENSE`;
- the folders listed in the README;
- `.github/` and the git configuration files.

Do not add files at the root.


**New result folders** are named `<YYYY-MM-DD>-<short-slug>`, for example `experiments/cycle_spectrum/2026-11-02-largest-letter-bound/`. Dates avoid ID collisions between parallel pull requests.

Legacy folders keep their historical IDs: `C001`–`C014`, `S02`–`S13`, `V001`–`V009`, and the R-series topic folders. [`docs/CONVENTIONS.md`](docs/CONVENTIONS.md) has the glossary.

**A new research line** needs an `experiments/<line>/README.md` and a row in [`experiments/README.md`](experiments/README.md). Open a line only when the work does not fit an existing one.

## 3. File-type rules

- **Markdown (`.md`)**
  - All prose is GitHub-flavoured Markdown, with one `#` title per file.
  - Link to other repository files by relative path. Never use absolute URLs to this repository or local filesystem paths.
  - Math may use Unicode, code spans, or GitHub's `$…$` LaTeX, but it must stay readable as plain text.
  - Mention files in prose by their repository-relative path, e.g. `experiments/cycle_spectrum/C011/REPORT.md`.
- **LaTeX (`.tex`):** only in `papers/<slug>/`. Each paper is one folder with its `.tex` and an optional `.bib`.
- **Python (`.py`)**
  - Python ≥ 3.10, standard library only. If a script truly needs a package, say so in the folder's README.
  - Scripts must run from the repository root as `python3 path/to/script.py`.
  - Locate files relative to `Path(__file__)`. Never hard-code absolute or user-specific paths.
  - Scripts must be deterministic, with fixed seeds and no wall-clock data in receipts.
  - **Default mode checks**: recompute and compare with the committed receipt, print a one-line summary, and exit non-zero on any failure.
  - `--write-receipt` rewrites the receipt.
  - Use `assert` only for internal invariants, because checks must also hold under `python3 -O`. Prefer explicit `if … raise`.
- **C/C++:** allowed for heavy enumeration. Put build instructions in the header comment, and wrap the program in a Python script that writes the receipt.
- **Lean (`.lean`):** only in `lean/`.
  - Only the standard axioms `propext`, `Classical.choice` and `Quot.sound` are allowed.
  - No `sorry`, `admit`, `native_decide`, new `axiom`s, `unsafe`, `implemented_by`, `extern` or `opaque` tricks.
  - Every new declaration's `#print axioms` output goes in `lean/receipts/`.
  - Record how the Lean statement matches the prose claim in `lean/STATE.md`.
- **Receipts (`.json`, `.csv`, `.txt`, `.log`):** produced by a committed script or build command and never edited by hand.
  - Do not embed machine-specific paths.
  - Files over 1 MB need a reason in the PR description. Prefer regenerating them on demand.
- **No other binaries:** no notebooks, images, archives or PDFs, unless a README explains why they are needed.

## 4. Status labels and claim discipline

Every result `README.md` starts with this header:

```markdown
# <Title>

- **Status:** formal | proved | written | conditional (inputs: …) | evidence | heuristic | open | refuted | withdrawn
- **Claim:** <one or two sentences, with all quantifiers and parameters>
- **Depends on:** <links to results and external inputs used>
- **Evidence:** <proof section / scripts and receipts / Lean declarations>
- **Authors:** <human and/or agent, including the model name>, <date>
- **Reviews:** <links, or "none yet">
```

| Label | Meaning |
|---|---|
| `formal` | Machine-checked in Lean in this repository, with receipts (§3). |
| `proved` | Complete written proof, independently reviewed: the review is in the repository. |
| `written` | Complete written proof, not yet independently reviewed. |
| `conditional` | Proved, at the stated level, assuming named inputs: an external theorem, a computational bound, or an explicit hypothesis. Always list the inputs. |
| `evidence` | Finite computation or data with a receipt. It supports a general claim but does not prove it. |
| `heuristic` | A non-rigorous argument or extrapolation. Label it in the text wherever it appears. |
| `open` | A stated target or question. |
| `refuted` | Shown false. Link the counterexample. |
| `withdrawn` | Retracted by its authors. Give the reason. |

Rules:
- **Never claim to prove the Collatz conjecture** or to exclude all cycles unless the full argument is `formal`. State exactly which class a result covers.
- **Scope every claim.** Give the map (`3x+1` or `3x+d`), the clock (odd-only or shortcut; never mix them), the class of cycles or words, and every bound and parameter.
- **Test against the controls.** Any argument about cycles must allow the actual cycles of `3x+5`, `3x+7`, `3x+13`, `3x+61` and the other tested parameters ([`docs/CONVENTIONS.md`](docs/CONVENTIONS.md) §3). An argument that would exclude them is wrong.
- **Compute before you quote.** Every number in a claim comes from a committed script whose receipt prints it. Do not quote estimates as results.
- **Label heuristics.** Do not derive probabilities from moment bounds.
- **Name external inputs.** Inputs that are not proved here, such as published bounds, replayed external Lean results, or period bounds from computation, are listed in [`docs/CONVENTIONS.md`](docs/CONVENTIONS.md) §5. A result using them is `conditional` on them.
- **Keep correctness, novelty and usefulness separate.** Check the literature ([`docs/LITERATURE.md`](docs/LITERATURE.md)) before calling anything new. Write "novelty undetermined" when unsure.
- **Never silently change a merged claim.** Corrections go in a new PR:
  - add a dated **Correction** note at the top of the affected file;
  - change the status label if needed;
  - update the index rows.
  - Wrong claims become `refuted` or `withdrawn`. They are never deleted.

## 5. Workflow

1. **Branch.** Work on a branch named `<handle>/<short-slug>`, from an up-to-date `main`. Never push to `main`, never force-push a shared branch, and never rewrite history.
2. **Keep it small.** One contribution per pull request: one result, one review, one formalisation, or one fix. Do not reformat or move unrelated files.
3. **Index it.** Add your result's row to its line's `README.md` index and to [`docs/RESULTS.md`](docs/RESULTS.md).
   - Change [`docs/STATUS.md`](docs/STATUS.md) only if the headline standing changes.
   - Change [`docs/FRONTIER.md`](docs/FRONTIER.md) if the frontier moves.
4. **Check.** Before opening the PR, run:

   ```sh
   python3 scripts/check_links.py              # every relative link resolves
   python3 scripts/run_checks.py --line <line> # the line's checkers still pass
   python3 path/to/your/check_<topic>.py       # your own checks, in check mode
   ```

   If you touched `experiments/packet_currents`, `experiments/current_construction`, `experiments/annular_construction`, `experiments/residual_progress` or `experiments/phase6`, also run `python3 scripts/verify_all.py`.
5. **Open the PR** with the template in [`.github/PULL_REQUEST_TEMPLATE.md`](.github/PULL_REQUEST_TEMPLATE.md). Disclose AI use: which agent or model, and how autonomous it was.
6. **Review.**
   - Results enter as `written`, `evidence`, `heuristic` or `conditional`. A result becomes `proved` only after an independent review, recorded in `reviews/` or in the result folder by someone other than the author.
   - Lean units become `formal` after a reviewer checks the receipts against the statement.
   - Do not merge your own PR. Maintainers merge.

## 6. Frozen material

Do not edit, rename or move anything in:
- `archive/`;
- the finished lines `experiments/packet_currents/`, `experiments/current_construction/`, `experiments/annular_construction/`, `experiments/residual_progress/`, `experiments/phase6/`, `experiments/viewpoints/` and `experiments/explicit_tao/`;
- every committed receipt and script of an existing result, in any line;
- `papers/right_aligned_reduction/`.

The reason is concrete. Scripts load each other's files by path, and receipts pin SHA-256 hashes of scripts, data and even notes. Changing one byte breaks the checks that keep the record reproducible. A broken link in a note may be fixed only if no receipt pins that note; run the line's checks afterwards.

Build on frozen material by adding new folders that cite it.

Some historical checkers are pinned to old commits and fail at `HEAD`. This is expected; they are listed in [`scripts/run_checks.py`](scripts/run_checks.py). Examples are the C008–C013 `check_delivery.py` scripts.

## 7. Hygiene

- No secrets, tokens, personal data or absolute local paths in any file.
- No generated caches (`__pycache__`, `.lake/`, build outputs). `.gitignore` covers the common ones.
- Never fabricate citations, results or receipts. If you cannot verify something, say so.
- When unsure whether something belongs in the repository, open an issue first.
